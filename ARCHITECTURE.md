# Solution Architecture

Решение построено на многоуровневой архитектуре платформы Doczilla, разделяющей логику документа, процесс его согласования, модуль интеллектуального извлечения данных и слой контроля качества.

## Уровень 1: Интерактивный шаблон документа
Отвечает за структуру, вариативность и финальный вид документа.
- **Словарь данных:** Единый реестр из 30–50 переменных с постоянными идентификаторами (field_id в формате snake_case, например, `contract.price`, `party.customer.inn`).
- **Условия и ветвления:** Не менее двух типов вариативности (альтернативные тексты пунктов и условное включение целых разделов или приложений). Поддержка вложенных условий (например, `payment.has_advance` -> `payment.advance_type`).
- **Мультипликаторы:** Динамические таблицы для повторяющихся данных (например, `services.items[]` с полями: наименование, объем, цена, сумма).
- **Экспорт:** Конфигурация шаблонов для генерации DOCX и PDF с корректной нумерацией, шапками таблиц и перекрестными ссылками.

## Уровень 2: Бизнес-процесс согласования
Отвечает за маршрутизацию документа между участниками.
- **Роли (Actors):** Юрист, Ведущий юрист, Бухгалтер, Менеджер, Коммерческий директор, Генеральный директор.
- **Этапы (Stages):** Проверка -> Согласование -> Подписание.
- **Правила маршрутизации (Routing):** Переходы между задачами, управляемые условиями на основе переменных шаблона (например, если `contract.price > 500000`, маршрут проходит через Коммерческого директора).

## Уровень 3: Модуль AI-автозаполнения (Контролируемое извлечение)
AI используется строго как модуль извлечения и сопоставления сведений, а не как генератор юридических условий.
- **Стратегия:** Извлечение фактов -> Нормализация (форматы дат, сумм) -> Привязка к field_id.
- **Статусы извлечения:** Для каждого поля модель возвращает строгий JSON со статусом:
  - `FOUND`: факт найден и нормализован.
  - `NOT_FOUND`: данных нет, value = null (модели запрещено "галлюцинировать").
  - `CONFLICT`: значения расходятся в разных частях документа (требует ручного решения).
  - `UNCERTAIN` / `NEED_CONFIRMATION`: формат не распознан или требуется юридическая трактовка.
- **Версионирование:** Поддержка минимум 3 версий промпта (базовая, с контролем пропусков, с обработкой конфликтов) для сравнения метрик.

## Уровень 4: Контроль качества (QA и Чек-лист)
Независимый слой валидации перед финальным экспортом.
- **Матрица правил:** 15–20 независимых проверок (полнота реквизитов, равенство сумм, корректность дат, отсутствие ссылок на несуществующие приложения).
- **Реакция на ошибки:** Система не скрывает дефекты. При срабатывании правила (FAIL или CONFLICT) пользователю предлагается конкретное действие (уточнить, пересчитать, принять ручное решение).

## Принципы интеграции компонентов
1. **Единый источник истины:** Переменная `contract.price` в шаблоне, в промпте AI и в правиле чек-листа имеет один и тот же field_id.
2. **Разделение ответственности:** AI извлекает факт, но решение о включении юридического пункта принимается на основе жестких правил шаблона или явного подтверждения пользователя.
3. **Прозрачность:** Для каждого заполненного поля сохраняется `source_quote` (цитата из источника), чтобы пользователь мог проверить корректность извлечения.

## Важное ограничение
Проверка чек-листом и генерация договора не означают, что документ юридически одобрен. Система демонстрирует инженерную корректность и прозрачность обработки; правовую экспертизу проводят уполномоченные специалисты.
